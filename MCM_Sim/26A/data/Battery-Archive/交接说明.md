# Battery-Archive 数据交接说明（面向 26A 赛题 A）

本文件用于把 `MCM_Sim/26A/data/Battery-Archive/` 的数据来源、结构、复现方式与“如何在赛题 A（智能手机电池耗电建模）中使用”交接给下一位工作者。

## 1. 这个目录在赛题 A 中的作用（为什么要放在这里）

赛题 A（见 `MCM_Sim/26A/论文/赛题/A中文纯文本.md`）要求建立**连续时间 SOC 模型**并做 TTE（Time-to-Empty）预测，且强调机理/物理意义而非纯离散拟合。

本目录提供的 BatteryArchive 数据的价值主要体现在：

1. **电池侧机理参数的“现实数据锚点”**：从公开的锂电测试数据中提取/验证容量衰减、效率、充放电电压曲线等，用于支撑模型中的参数范围与合理性（而不是“拍脑袋”）。
2. **把“手机用电负载模型”与“电池模型”解耦**：手机端（屏幕/CPU/网络/GPS/后台）决定电流/功率负载；电池端用 BatteryArchive 的真实电芯数据来定义“在给定电流、温度、老化程度下，SOC/电压如何演化”。
3. **支撑敏感性分析与老化讨论**：循环测试数据可用于讨论有效容量随循环/时间变化、不同化学体系差异；破坏测试数据可用于扩展讨论安全/温升（可选，不一定是主线）。

重要：BatteryArchive 的数据并非“手机整机功耗日志”，它是**电芯层面**数据。赛题 A 的主线通常是：

`手机负载（I(t) 或 P(t)）` + `电池连续时间模型（SOC(t), V(t), Q_eff(t), R_int(t)）` -> `TTE`

BatteryArchive 主要用于第二部分（电池侧）。

## 2. 数据来源与抓取方式（你接手后如何复现）

BatteryArchive.org 的“Cycling tests / Disruptive tests”页面通过 iframe 嵌入 Redash 公共仪表板。本目录通过 **Redash Public API** 导出数据：

- `https://database.batteryarchive.org/api/dashboards/public/<token>`：获取 dashboard 元数据（含 query id / 参数默认值）
- `POST https://database.batteryarchive.org/api/queries/<id>/results?api_key=<token>`：按参数运行 query 并返回 JSON（脚本将其落为 CSV）

关键点：这里的 `api_key` 使用的是 **public dashboard token**（不是用户登录后的 API key）。

## 5. 完整性/缺失检查（结论与复验方法）

结论（以当前目录状态为准）：

- `extracted/cycling/*.tar.gz`：每个压缩包内 CSV 数量 == cycling 的唯一 cell_id 数（137）；
- `extracted/disruptive/*.tar.gz`：每个压缩包内 CSV 数量 == disruptive 的唯一 cell_id 数（72）。

也就是说：在“以 cell_id 为键导出逐 cell 数据”的口径下，**没有遗失或缺失**。

你可以用下面脚本快速复验（不解压，仅统计 tar 里文件名并与 cell_list 对比）：

```bash
python3 - <<'PY'
import csv, tarfile
from pathlib import Path
from urllib.parse import unquote

root = Path("MCM_Sim/26A/data/Battery-Archive")

def read_ids(p: Path):
    s=set()
    with p.open(newline="", encoding="utf-8") as f:
        for r in csv.DictReader(f):
            cid=(r.get("cell_id") or "").strip()
            if cid:
                s.add(cid)
    return s

def ids_in_tar(p: Path):
    s=set()
    with tarfile.open(p, "r:gz") as tf:
        for m in tf.getmembers():
            if not m.isfile() or not m.name.endswith(".csv"):
                continue
            name=Path(m.name).name
            if name.startswith("._"):
                continue
            s.add(unquote(name[:-4]))
    return s

for cat in ["cycling", "disruptive"]:
    ids = read_ids(root / "extracted" / cat / "cell_list.csv")
    print(cat, "unique cell_id =", len(ids))
    for tar in sorted((root / "extracted" / cat).glob("*.tar.gz")):
        present = ids_in_tar(tar)
        miss = sorted(ids - present)
        print(" ", tar.name, "present", len(present), "missing", len(miss))
        if miss:
            print("   missing sample:", miss[:10])
PY
```

## 6. 如何把这些数据用进赛题 A 的模型（建议路线）

### 6.1 建模结构建议（满足“连续时间”要求）

常见可行结构（示例）：

- SOC 状态方程（库仑计量）：
  - `dSOC/dt = - I(t) / Q_eff(t, T, age)`（连续时间 ODE）
- 电压模型（可选但建议）：
  - `V(t) = OCV(SOC, T) - I(t) * R_int(SOC, T, age)`（等效电路/半经验）
- 老化/有效容量演化（可选，用于“历史”因素）：
  - `dQ_eff/dt = -k(...)` 或用循环数据拟合 `Q_eff(n_cycle)` 再映射到时间尺度

其中：

- `I(t)` 或 `P(t)` 来自你对手机使用场景的建模（屏幕/CPU/网络/GPS/后台等）。
- BatteryArchive 用于支撑 `Q_eff`、效率、以及电压相关曲线的合理范围与形状。

### 6.2 从 BatteryArchive 能直接提取的量（对应文件）

循环测试（cycling）：

- 容量/能量随循环的变化：`energy_and_capacity_decay.tar.gz`
- 效率相关（库仑效率/能量效率等，具体看 CSV 的 `series`）：`efficiencies.tar.gz`
- 充/放电电压曲线切片：`charge_voltage_by_step.tar.gz`、`discharge_voltage_by_step.tar.gz`
- 每循环的电压统计（最大/最小/均值等，具体看 `series`）：`max_and_min_voltage_by_cycle.tar.gz`

破坏测试（disruptive）：

- 电压/力/位移/温度的时间序列：对应 `disruptive_test_*.tar.gz`
  - 这部分更偏“安全/热失控/机械触发”情景，是否纳入取决于你论文叙事。

### 6.3 “更像手机电池”的筛选建议

手机电池通常是 **pouch（软包）+ NMC/Graphite**（或类似体系），容量大致在 3–6Ah（机型不同）。

可用 `extracted/cycling/cell_list.csv` 先筛选：

- `form_factor == pouch`
- `cathode` 选择 NMC（或 NMC-LCO 等）
- `temperature` 优先 25C/40C（与常温/高温情景对应）
- `ah` 选择接近手机容量的量级（例如 2.8Ah / 3Ah / 3.4Ah / 5Ah）

然后只解压/使用对应 cell_id 的 CSV（避免全量）。

### 6.4 Cell ID 命名规则速记（来自 BatteryArchive Metadata）

BatteryArchive 的 cycling 数据中，`cell_id` 通常按如下结构组织（括号表示可选）：

`机构代码_(原始cell编号)_外形_cathode_温度_最小SOC-最大SOC_充电倍率/放电倍率_(字母)`

例：

- `CALCE_CS2-8_prism_LCO_21C_0-100_0.5/0.5C_a`
- `OX_1-1_pouch_LCO_40C_0-100_2/1.84C_a`（放电倍率可能是某个 duty cycle 的平均倍率）

本目录的逐 cell CSV 文件名是对 `cell_id` 做 URL 编码后的结果（为了避免文件名中的 `/` 等字符造成路径问题）。

## 8. 维护与常见问题

1. **token 会不会变？**  
   可能会。脚本通过 `sources/cycle_list.html` 等页面解析 token；若网站更新导致 token 改变，需要重新抓取这些页面（删除 `sources/*.html` 后重跑脚本，或手工更新）。

2. **为什么用 tar.gz？**  
   逐 cell CSV 数量多、体积大。脚本会按 query 打包成 `tar.gz`，显著节省磁盘空间，便于交付与版本管理。

3. **disruptive cell_list 为什么有重复 cell_id？**  
   Cell List 里同一 `cell_id` 可能对应多条测试记录（不同 indentor/nail_speed 等字段）。当前 Redash 的数据查询主要以 `cell_id` 为参数，因此逐 cell 导出按“唯一 cell_id”组织更一致；如需区分这些重复记录，需要进一步研究 dashboard 的 query 定义是否支持额外参数（当前公开 dashboard 未暴露）。

4. **如果需要“更全/更原始”的数据怎么办？**  
   BatteryArchive 首页与 FAQ 提到，部分完整/批量数据可能需要通过其公开渠道联系获取；本目录仅基于当前可访问的 public dashboard 数据导出。
